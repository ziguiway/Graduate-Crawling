## 核心知识点 1：正向最大匹配算法（FMM）

### 算法思路

从左到右扫描文本，每个位置尝试匹配词典里最长的词；匹配到就切出来，指针前移；都匹配不上就把当前单字当成一个词。

### 伪代码

```
max_len = 词典里最长词的长度
i = 0
while i < len(text):
    j = max_len
    while j > 0:
        word = text[i : i+j]
        if word in 词典:
            输出 word
            i += j
            break
        if j == 1:   # 单字兜底
            输出 text[i]
            i += 1
            break
        j -= 1
```

### 为什么叫"正向"+"最大"

- **正向**：从左到右扫描（反向最大匹配则是从右到左）
- **最大**：每个位置优先匹配最长的词（贪心）

### 算法缺陷

最大匹配是**贪心**，只看局部最长，不考虑上下文。典型错误：

| 答案 | FMM 输出 | 问题 |
|---|---|---|
| `中国 / 人民` | `中国人 / 民` | 词典里有 `中国人`，贪婪匹配就切错了 |
| `结婚 / 和 / 已婚` | `结婚 / 和已 / 婚` | 词典里有 `和已`，切错 |

这种错误**无法通过算法本身修复**，需要更好的模型（HMM、CRF、神经网络）才能解决。这也是后面作业的演进方向。

### 我的实现

```python
def split_word(word_list, text):
    result = []
    max_len = get_dic_max_len(word_list)
    i = 0
    while i < len(text):
        j = max_len
        while j > 0:
            word = text[i:i+j]
            if word in word_list:
                result.append(word)
                i = i + j
                break
            if j == 1:
                result.append(text[i])
                i += 1
                break
            j -= 1
    return result
```

> [!warning] 我的实现的已知缺陷
> `text = "\n".join(...)` 把多行拼成一整段，`'\n'` 被当成普通字符参与词典匹配。
> 实际上 `'\n'` 不在词典里，会走 `j==1` 分支被当单字 append 进 result。
> 这虽然不影响最终输出（因为写文件时 `'\n'` 被还原成换行），但语义上不干净。
> 更好的做法：按行处理，每行单独跑 `split_word`。

## 核心知识点 2：分词评价指标 P / R / F

### 三个基础量

| 量                  | 含义                 | 公式        |
| ------------------ | ------------------ | --------- |
| 正确切分数 (correct)    | 你的切分中**位置也对**的词数   | 见下方"对齐方式" |
| 你切出的总词数 (total_my) | `MyOut.txt` 里的词总数  | 数词数       |
| 答案总词数 (total_ans)  | `Answer.txt` 里的词总数 | 数词数       |

### P / R / F 公式

```
P (精确率) = correct / total_my      你的切分里有多少是对的
R (召回率) = correct / total_ans      答案里有多少被你切对了
F (F值)    = 2PR / (P+R)              P 和 R 的调和平均
```

### 为什么不能用"位置对齐"？

直觉做法：逐位置对比 `my_line[i] == ans_line[i]`。但这会**错位**：

- 答案：`中国 / 人民 / 银行 / 行长`（4 个词）
- FMM：`中国人 / 民 / 银行 / 行长`（4 个词）

逐位置对比：

| 位置 | 答案 | FMM | 相等？ |
|---|---|---|---|
| 0 | 中国 | 中国人 | ❌ |
| 1 | 人民 | 民 | ❌ |
| 2 | 银行 | 银行 | ✅ |
| 3 | 行长 | 行长 | ✅ |

`中国` 和 `人民` 本身是对的（位置 0、1 切分点正确），但因为前面错位，被算成错误。**位置对齐会低估 correct**。

实测：位置对齐版 `correct=19277`，比老师给的 20263 少 986。

### 标准做法：字符边界对齐

把词列表转成"**切分边界位置**"集合，两个集合求交集：

```
['中国', '人民']  → 累积字符位置 {2, 4}   （第 2、4 字符后有切分边界）
['中国人', '民']  → 累积字符位置 {3, 4}   （第 3、4 字符后有切分边界）

交集 = {4}  → correct = 1
```

为什么这样对？因为分词的本质就是"在哪些字符后画切分线"。只要切分线位置对了，词就对；不用管词被切成几个、词长是否一致。

### 我的实现

```python
def boundaries(words):
    """['中国','人民'] → {2, 4}"""
    pos = 0
    b = set()
    for w in words:
        pos += len(w)
        b.add(pos)
    return b

def evaluate(my_words_per_line, answer_words_per_line):
    correct = 0
    total_my = 0
    total_ans = 0
    for my_line, ans_line in zip(my_words_per_line, answer_words_per_line):
        correct += len(boundaries(my_line) & boundaries(ans_line))
        total_my += len(my_line)
        total_ans += len(ans_line)
    return correct, total_my, total_ans
```

### 我的评价结果

| 指标        | 我的值     | 老师值     | 差距       |
| --------- | ------- | ------- | -------- |
| total_my  | 20397   | 20397   | ✅ 完全一致   |
| total_ans | 20454   | 20454   | ✅ 完全一致   |
| correct   | 20358   | 20263   | +95      |
| P         | 0.99809 | 0.99343 | +0.00466 |

> 三个量都在 0.99 量级，吻合度足够高，不影响学习目标。

## 核心知识点 3：数据加载的细节

### `split()` vs `split(" ")`

```python
"中国 人民 ".split(" ")    # → ['中国', '人民', '']    末尾空字符串
"中国 人民 ".split()       # → ['中国', '人民']         自动忽略空白
```

读词列表时一定要用 `split()`（不传参数），否则末尾的空字符串会污染词数。

### 按行加载

```python
def lode_file(file_path):
    with open(file_path, 'r') as fp:
        lines = [line.strip("\n") for line in fp.readlines()]
    return lines
```

`strip("\n")` 只去换行，保留行内空格。如果用 `strip()` 会把行首行尾的所有空白都去掉，可能影响边界对齐（虽然本作业里不影响）。

## 我踩过的坑

### 坑 1：以为"输出和 Out.txt 一致"就等于"评价正确"

**现象**：`diff MyOut.txt Out.txt` 无输出，以为作业做完了，但老师给的 4 个数字（20263 等）对不上。

**根因**：分词算法对 ≠ 评价算法对。`Out.txt` 只是**分词结果**，老师给的 20263 是**评价结果**，是另一个步骤算出来的。

**改法**：单独写 `evaluate()` 函数，把分词结果和 `Answer.txt` 对比算 P/R/F。

> [!lesson] 一句话记忆
> 分词（生成）和评价（打分）是两件事，作业要求两件都做。

### 坑 2：位置对齐版低估 correct

**错误代码**：
```python
for i in range(len(split_text)):
    if split_text[i] == split_answer[i]:
        count += 1
```

**问题**：一旦某处切分不一致（`中国` vs `中国人`），后面所有词位置错位，即使本身是对的也被算错。

**改法**：用字符边界对齐——把词列表转成切分边界位置集合，求交集。

> [!lesson] 一句话记忆
> 分词评价看"切分线位置"，不看"词在第几位"。线对了，词就对。

### 坑 3：位置对齐版 `split_answer[i]` 越界

**错误代码**：
```python
for i in range(len(split_text)):
    if split_text[i] == split_answer[i]:   # split_text 更长时 IndexError
```

**问题**：你的切分词数（20397）和答案词数（20454）不相等，`i` 超出较短的那个就崩。

**改法**：用 `zip` 自动按较短的配对，或 `range(min(len(a), len(b)))`。

> [!lesson] 一句话记忆
> 两个列表逐位置对比，用 `zip`，不要用 `range(len(...))`。

### 坑 4：函数里嵌套定义函数

**错误代码**：
```python
def evaluate(...):
    for ...:
        def boundaries(words):   # 每次循环都重新定义一遍
            ...
        correct += len(boundaries(my_line) & boundaries(ans_line))
```

**问题**：循环体里定义函数，每次迭代都重建一次函数对象，浪费；读起来也乱。

**改法**：把 `boundaries` 提到模块顶层。

> [!lesson] 一句话记忆
> 辅助函数提到模块顶层，不要在循环里嵌套定义。

### 坑 5：`boundaries` 抽象让代码变难读

**过程**：引入 `boundaries` 函数后，`evaluate` 变简洁了，但要先理解 `boundaries` 才能看懂 `evaluate`。

**反思**：抽象本身是对的（边界对齐必须有这一步转换），但**清晰度问题靠注释和命名解决，而不是靠取消抽象**。换回位置对齐虽然代码短，但算法是错的。

> [!lesson] 一句话记忆
> 简洁不等于正确。用对算法 + 写清楚注释，比用错算法 + 代码短更重要。

## 我的理解

这次作业表面上是"分词 + 评价"，真正学到的东西：

1. **分词和评价是两件事**。我一开始以为 `diff MyOut.txt Out.txt` 一致就完事了，完全没想到老师给的 20263 是另一套算法算出来的。这让我意识到：**"做出结果"和"评价结果"在 NLP 里是分开的两步**，后面 HMM、CRF 作业都会涉及评价，必须把 P/R/F 算法吃透。

2. **位置对齐 vs 边界对齐**是个反直觉的点。直觉上"逐位置对比词"看起来对，但只要错位就全错。换成"对比切分边界"才正确。这个教训让我以后遇到"对齐"类问题会先想：**对齐的粒度是什么？字符？词？还是某种边界？**

3. **贪心算法的局限是结构性的**。FMM 切错 `中国人/民` 不是 bug，是贪心本质决定的——只看局部最长，不顾全局。修不了，只能换更好的模型。这正好解释了为什么后面要学 HMM（用概率模型考虑上下文）、CRF（用全局序列模型）、BiLSTM（用神经网络学上下文表示）。每个模型都是在解决前一个的局限。

4. **老师说的"不要直接看别人代码"再次应验**。如果我直接抄一个评价脚本，永远不会撞上"位置对齐会错位"这个坑，也就不会真正理解为什么 NLP 分词评价要用边界对齐。撞过坑、调试过、改对过，这个知识才是我的。
