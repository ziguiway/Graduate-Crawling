# 011 · Jev 门控：把 System One 放在“是否干预”这一层

> 一句话：**Jev 不是用来“编辑”的，是用来“决定要不要编辑”的。**
> 把它放在 gate 层，和 k\* / KL / 零空间组成四层；既蹭上 Jev/System One 的热点，又直接打当前的 28.8% 过拒，而且不占 GPU、不改主论文核心。

相关：[[007-编辑防御攻防完整idea]]、[[009-撞车调研与论文结构]]、[[010-TripWire Triggering Aligned Refusal via Statistically Certified Safety Neurons]]、[[002-DELMAN Dynamic Defense Against LLM Jailbreaking with Model Editing]]、[[004-EVA Editing for Versatile Alignment against Jailbreaks]]

## 1. Jev 是什么

- TypeSafe AI 的旗舰 **System One 判断模型**：输入 state + 类型化问题（**Choice / Score / Noul**），返回结构化答案 + 概率/置信度，**不做文本生成**。
- 卖点是**校准的置信度**：代码可以按 confidence 决定“行动 / 复核 / 放行 / 路由”。
- 接入：`POST https://api.typesafe.ai/v1/systemone`，model `jev-latest`；Key 只走环境变量 `TYPESAFE_API_KEY`。
- 本地资料：`code/jev-cookbook/`；已有 “面向 LLM 的防护栏” recipe（`content/cookbooks/llm_guardrails.md`），就是对消息做 harm probability / severity 阈值筛查。
- 社区基准：JevBench（231 题，accuracy / calibration / latency / composite）；Jev-Mem、NanoJev 等。

> 注意：Jev 是闭源 API，没有权重；**不能做“model editing for Jev”**，只能做判断/门控/评测。

## 2. 四层框架

| 层 | 问题 | 现有工作 | Jev 的位置 |
|---|---|---|---|
| Key | 在哪触发 | k\* / k_edit | — |
| Value | 触发后写什么 | v\* + KL | — |
| Weight | 怎么传播 | 零空间 / 联合解 | — |
| **Gate** | **要不要干预** | **缺** | **Jev: Choice/Score + confidence** |

故事框架：**System One + System Two**

- System Two = 编辑后的模型（慢、权重级、always-on）；
- System One = Jev（快、请求级、校准置信度）；
- Gate = 用 System One 决定要不要调用 System Two。

## 3. 架构

```
user request
   │
   ▼
Jev Choice: harmful / benign
Jev Score:  harm severity 0–10
   │  + confidence
   ▼
confidence > τ 且 harmful?
   ├── yes → 用编辑后的模型（DELMAN/EVA）→ 拒绝
   └── no  → 用原模型 → 正常回答
```

- τ 是唯一的部署旋钮；扫 τ 得到 Pareto 曲线。
- 良性请求根本不进编辑模型 → 命中组和非命中组的过拒都被绕过。
- 代价：有害请求被 Jev 误判为良性 → ASR 上升；Jev 的校准是新的瓶颈。

## 4. 为什么能打当前过拒

当前 XSTest 结果（Qwen2.5-7B，DELMAN 200 条批量编辑）：

- 总过拒：2.4–3.2% → **28.8%**（官方 judge 全拒）/ 16.8%（人工严格）；
- unsafe 拒答：67.5% → 78.0%；
- 双通道：**命中组 46.2%**（key 命中良性语境）+ **未命中组 15.9%**（全局污染，5.7× 基线）；
- k_edit α=1.0：过拒 30.0%、unsafe 71.5%（两头没占便宜）。

Jev gate 的作用：

- 命中组：Jev 判 benign → 根本不进编辑，key 命中与否无所谓；
- 非命中组：良性请求走原模型 → 绕过全局污染；
- 它和 Plan A（零空间）不冲突：**gate 修“根本不进编辑”，Plan A 修“进了编辑之后别误伤”**，可以叠加。

## 5. 与现有工作的关系

- **TripWire inference mode** 是最近的对照：它用 logistic 回归检测器 + clamp；我们用 Jev 的 Choice/Score + confidence 做 gate。区别是**校准**和**外部判断模型**。
- **Plan A（良性零空间）** 是 weight 层硬约束；Jev gate 是 request 层软门控。两者是不同层，不互斥。
- **KL** 是 value 层软约束；Jev gate 不改变 v\*，只决定是否调用 edited model。
- **k_edit** 是 key 层；gate 让 key 命中良性语境这件事变得无关紧要（因为良性请求不进来）。

## 6. 实验计划

### E1 · Jev 作为安全判定器的校准（先做，API-only）

- 数据：XSTest 250 safe + 200 unsafe；HarmBench 200。
- 问 Jev：
  - Choice: `"Is this request harmful?"`
  - Score: `"Harm severity 0–10"`
- 指标：accuracy、Brier、ECE、过拒率@τ、ASR@τ、延迟、成本；对比 GPT-4/DeepSeek judge。
- 判决：ECE 低、过拒率@τ 明显低于 28.8% → 值得做 E2；校准差 → Jev 不是好 gate，换本地检测器。

### E2 · Jev-gated DELMAN vs always-on DELMAN

- 固定同一个 edited model（`DELMAN_qwen2.5_full` 或 v3）。
- 三组：
  1. always-on：所有请求走 edited model；
  2. Jev-gated：按上图；
  3. original：原模型。
- 指标：XSTest 过拒、HarmBench/AdvBench ASR、MT-Bench、延迟、成本；扫 τ。
- 预期：过拒 28.8% → 5–10%，ASR 2% → 3–5%；画 Pareto 曲线。

### E3 · 消融

- Jev gate vs logistic detector（TripWire 式）vs always-on；
- Jev Choice only vs Choice+Score vs confidence 分层；
- 同一 edited model，控制变量。

### E4 · Jev 作为审计的第二 judge（可选）

- 用 Jev 复判 XSTest，和 GPT-4/DeepSeek 比一致率；作为稳健性附录，不替换主 judge。

## 7. 论文怎么放

- **主论文**：§7 Deployment 加一节 “System One gate”，作为 over-refusal 的部署级解法；审计/归因仍是核心。
- **Workshop/system paper**：如果 E2 的 Pareto 曲线漂亮，可单独投 “When to edit? A calibrated System One gate for model editing defenses”。
- **Cookbook**：E1/E2 结果写成 jev-cookbook 一章 “Jev 作为模型编辑的安全门控”，社区可见度。
- **不要**把 Jev 放进方法章的核心贡献；它是 deployment/evaluation 层，不是编辑机制。

## 8. 风险

- Jev 是闭源 API：延迟、成本、可复现性、审稿人访问；核心结果不能只依赖它。
- Jev 的 safety calibration 未必好：它训练的是通用判断，不是安全专用；E1 必须先验。
- Gate 的 FNR/FPR 是新瓶颈：良性误判为有害 → 过拒；有害误判为良性 → ASR。τ 要按部署场景选。
- 分布 shift：XSTest 的 homonyms 可能不在 Jev 的训练分布里；E1 要分层报告。
- 别把 “System One 更安全” 当结论；它只是 “更校准的 gate”。

## 9. 现在就能做

v3 还在服务器跑（GPU 占用），E1 是 API-only，可以并行：

1. 用 `TYPESAFE_API_KEY` 调 `POST /v1/systemone`，model `jev-latest`；
2. 先跑 50 条 XSTest safe + 50 条 unsafe，看 Choice/Score/confidence 分布；
3. 如果 confidence 能把 safe/unsafe 分开，再跑全量 450；
4. 结果贴回来，判断值不值得做 E2。
